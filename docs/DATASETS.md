# Dataset research and acquisition

Research checked . A suitable benchmark must pair captured/rendered room observations with metric geometry. A dataset of floor-plan drawings alone cannot evaluate capture-to-plan reconstruction.

## Selected and downloaded

**V2 acquisition:** three ARKitScenes venues are now local: development video
`41418135` (visit `416418`), held-out `41418140` (`416411`) and `41418155`
(`416407`). RGB, low-resolution mobile depth, confidence, calibration and sensor
trajectories were downloaded. One FARO station per venue is stored separately
under `datasets/arkitscenes/references/` (about 1.9 GB per station). Source URLs,
hashes and sizes are recorded in `datasets/arkitscenes/SOURCE.json` and
`datasets/reference_acquisition.json`. The [provider terms](https://github.com/apple/ARKitScenes/blob/main/LICENSE)
apply. High-resolution reference depth is never used as mobile LiDAR input.

ICL trajectory 1 is also acquired (194 sampled pairs), held out from the original
trajectory-2 development. It shares room geometry and is not a new property.
The controlled multiroom fixture is independently generated by this repository;
it is not a public real-world benchmark. Exact simulated sensor poses are
disclosed for its LiDAR branch, while its RGB branches receive no poses/depth.

```powershell
& .\.venv\Scripts\python.exe scripts\prepare_arkit.py datasets\arkitscenes --count 3
& .\.venv\Scripts\python.exe scripts\acquire_references.py datasets
& .\.venv\Scripts\python.exe scripts\prepare_icl.py datasets\icl_nuim\living_room_traj1_frei_png.tar.gz datasets\icl_nuim\trajectory1 --stride 5
& .\.venv\Scripts\python.exe scripts\make_multimodal_fixture.py datasets\controlled_demo
& .\.venv\Scripts\python.exe -m floorplan.cli benchmark datasets\controlled_demo\suite.json --out demo\controlled_results
```

The ARKitScenes adapter selects synchronized timestamps before downsampling:
naively selecting 60 Hz depth frames discards most matches to lower-rate poses.
Laser inspection and annotation tools operate independently of reconstruction.
The one provisional reference uses manually inspected wall regions and robust
line fits; scanner coverage and annotation uncertainty remain explicit.

| Dataset | Available input and reference | What it tests here | Important limit |
| --- | --- | --- | --- |
| [ICL-NUIM living room](https://www.doc.ic.ac.uk/~ahanda/VaFRIC/iclnuim.html) | Synthetic RGB/depth sequence, camera calibration, ground-truth trajectory, separate surface mesh | Automatic RGB-D reconstruction; photo/video SfM; dimension comparison to room-floor mesh | One synthetic room; not actual phone LiDAR or a multi-room benchmark |
| [TUM RGB-D, Freiburg 1 room](https://cvg.cit.tum.de/data/datasets/rgbd-dataset) | Real RGB movie and camera trajectory downloaded earlier | Media decoding and difficult real RGB reconstruction | Trajectory truth does not provide room dimensions |

ICL-NUIM data uses CC BY 3.0; attribution and file hashes are in [SOURCE.md](../datasets/icl_nuim/SOURCE.md). The reference mesh archive is about 7.4 MB and trajectory-2 archive about 430 MB. The local adapter extracts every fifth frame: 177 RGB/depth pairs. The photo experiment samples 45 images from the same sequence; the video is encoded from those 177 RGB frames. These are input-path tests from one underlying scene, not three independent datasets.

The RGB-D algorithm receives the public intrinsics and metric depth scale, which are legitimate sensor calibration inputs. It receives neither reference camera poses nor floor polygons. The evaluator reads the held-out room-floor mesh after a plan is saved. The mesh-sampled wall experiment is explicitly labelled an oracle component test.

## Strong candidates for broader validation

| Candidate and official source | Why it is relevant | Access / remaining work |
| --- | --- | --- |
| [FloorNet](https://github.com/art-programmer/FloorNet) | Phone-based RGB-D residential scans paired with floor-plan annotations; closest match to multi-room task | Official annotation archive downloaded for inspection. Raw scan archive not downloaded. Verify coordinate-to-metre mapping and dataset terms before using it as a metric benchmark; legacy TensorFlow/Python implementation needs adaptation |
| [ARKitScenes](https://github.com/apple-aiml-research/ARKitScenes) | Actual Apple mobile LiDAR RGB-D data and reference laser depth | Best next mobile-sensor test; requires data adapter, sensor/pose conventions, and separate structural floor-plan reference extraction. Object boxes are not room polygons |
| [ScanNet++](https://scannetpp.mlsg.cit.tum.de/scannetpp/) | iPhone/DSLR observations with high-quality scans | Good cross-tier geometry candidate; access terms and per-scene download size need checking before acquisition |
| [ZInD](https://github.com/zillow/zind) | Real 360-degree home imagery and floor-plan annotations with a metric scale field | Data is restricted to approved academic use. Not selected for this company take-home. Panoramas also differ from ordinary perspective phone photos |
| [Structured3D](https://structured3d-dataset.org/) | Synthetic multi-room imagery, depth and explicit structure annotations | Strong automated topology benchmark; download requires agreement/access process. Keep synthetic and field results separate |
| [SceneCAD](https://github.com/skanti/SceneCAD) | Annotated room shells associated with ScanNet scans | Useful non-rectangular layout reference; requires matching ScanNet data/access and coordinate handling |

We also inspected [CubiCasa5k](https://github.com/CubiCasa/CubiCasa5k). Its floor-plan image annotations are useful for drawing interpretation, but it does not provide the paired phone captures needed for this task. Kaggle mirrors should be checked against the original provider for geometry, scale and provenance; choosing a convenient floor-plan image download would test the wrong input problem.

## Reproduce the chosen dataset preparation

From the repository root in PowerShell:

```powershell
New-Item -ItemType Directory -Force datasets\icl_nuim
curl.exe -L --retry 3 https://www.doc.ic.ac.uk/~ahanda/VaFRIC/living_room_obj_mtl.tar.gz -o datasets\icl_nuim\living_room_obj_mtl.tar.gz
curl.exe -L --retry 3 https://www.doc.ic.ac.uk/~ahanda/living_room_traj2_frei_png.tar.gz -o datasets\icl_nuim\living_room_traj2_frei_png.tar.gz
& .\.venv\Scripts\python.exe scripts\prepare_icl.py datasets\icl_nuim\living_room_traj2_frei_png.tar.gz datasets\icl_nuim\trajectory2 --stride 5
& .\.venv\Scripts\python.exe scripts\make_sequence_video.py datasets\icl_nuim\trajectory2\sequence.json datasets\icl_nuim\trajectory2.mp4 --fps 6
```

The [provider's calibration documentation](https://www.doc.ic.ac.uk/~ahanda/VaFRIC/codes.html) uses negative `fy` in its native convention. The adapter explicitly uses positive `fy` with OpenCV's y-down camera axes. For trajectory evaluation, the reference's native y-axis is reflected before a proper rigid alignment; scale is fixed at one. Frame 0 has no matching reference timestamp and is excluded from the trajectory score. Depth values in the TUM-compatible archive are divided by 5000 to obtain metres.

## What would establish the full claim

Use several properties, paired across photos, RGB video and actual phone LiDAR. Reserve independent laser/survey dimensions and room-corner coordinates. Include different devices, clutter, reflectivity, room shapes and doorway connections. Evaluate held-out properties; do not reuse a scale control as a test dimension. Report rejected/partial outputs alongside errors, and score missing/extra rooms and openings. One synthetic rectangle and a noisy wall-sampling test cannot validate that full claim.
